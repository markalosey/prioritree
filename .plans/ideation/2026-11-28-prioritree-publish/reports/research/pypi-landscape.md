(1) THE ARTIFACT FORMS — the two forms, what each carries

THE SDIST (source distribution): a tarball — .tar.gz the standard, normalized form (PEP 625: the filename {normalized_name}-{version}.tar.gz; the name PEP 503-normalized — lowercased, [-_.] runs collapsed to "-"; the .zip sdist the legacy outlier on the sources' deprecation path). Carries: the source tree + the packaging files (pyproject.toml per PEP 518/621; the build-backend contract per PEP 517) + PKG-INFO (the metadata file at the archive root) + package data. The consumer BUILDS at install time — pip invokes the build backend on the target machine; the sdist the rebuildable ground of the ecosystem. Source: the packaging user guide's "Source Distributions (sdist)" + PEP 625/517/621.

THE WHEEL (binary distribution): a zip archive renamed .whl (PEP 427, the Binary distribution format). No build at install — unpack + place into site-packages. Carries: the importable package + the .dist-info/ directory (METADATA — the core metadata file; WHEEL — the wheel's own metadata; RECORD — the installed manifest) + package data (the web's static assets + the MCP's server ride here per the packaging cure — tansa's lane prices the actual bytes).

THE FILE-NAME LAWS: the wheel {distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl (PEP 427/425) — prioritree-1.0.0-py3-none-any.whl the PURE-PYTHON form (py3-none-any: no ABI binding, any platform — the form a pure library ships); compiled extensions carry cp312-cp312-manylinux_2_17_x86_64 / macosx_11_0_arm64 / win_amd64 (the Platform compatibility tags specification defines the vocabulary + the tag expansion). THE VERSION'S TAG FORM (PEP 440): the release segment N[.N]* (1.0.0); the pre-release suffixes a/b/rc + number (1.0.0a1/b2/rc1 — sorted before the final); .postN post-releases; .devN dev; +local (stripped at the index).

WHAT THE INDEX ACCEPTS (PyPI's help, file formats): the two forms only — wheels (.whl) + sdists (.tar.gz; the .zip legacy) — no other upload forms; every file's name unique ACROSS THE INDEX forever; the upload channel the legacy endpoint at upload.pypi.org (twine / pypa/gh-action-pypi-publish POST there).

THE SIZE LIMITS (PyPI's help, file size limits): 60 MiB per file the default; maintainers may REQUEST an increase — the current maximum 1 GiB per file. Prioritree's pure-python pair sits far under the 60 MiB default — no constraint at this scale.

THE FIELDS (each field's form -> what the index page renders):

- Version — PEP 440 (above); renders the page header + the release-history sidebar.
- Summary — ONE line (the spec's 512-character bound); renders the page's subtitle; the search index's match line.
- Description (the long_description/readme) — the long-form body; PEP 621's readme (file + content-type) renders into Description; the index page renders it as the page BODY: markdown (text/markdown, README.md) or reStructuredText (text/x-rst), raw HTML stripped/sanitized; the README's public story (the Auth/Multi-user/Journey sections) serves HERE — the provenance ruling's public surface.
- THE AUTHOR FIELDS' FORMS — four fields: Author (name only), Author-email ("Name <email>" the RFC-822 form, multiple allowed), Maintainer, Maintainer-email; the spec prefers the -email forms (the identity carried whole; the name-only fields the legacy companions); the page renders the author/maintainer NAMES at the left sidebar (the -email fields' name parts the preferred carrier; emails never rendered) — the collaborator's name read at the index rides these fields (the account ruling's landing).
- License — THREE forms at the sources: (a) the License field (free text; deprecated in the metadata 2.4 line); (b) the license classifiers (License :: OSI Approved :: MIT License — the trove vocabulary); (c) PEP 639's License-Expression (SPDX: "MIT") + License-File (the LICENSE carried into the wheel) — the modern pair, the license classifier on the deprecation path; the page renders whichever form carries it; the CI effort's MIT cure prices the choice (the design rules the exact form).

- THE CLASSIFIERS — the CLOSED vocabulary, governed at pypi.org/classifiers (the pypa/trove-classifiers repository): "Development Status :: 1..7", "Intended Audience ::", "Programming Language :: Python :: 3.x" (one per supported version), "License :: OSI Approved ::", "Operating System :: OS Independent"; an unratified classifier string REFUSED at upload (the closed vocabulary enforced at the index); rendered the sidebar grouped.

(3) THE TWO CHANNELS — trusted publishing vs the API token (each channel's mechanics + its custody price)

TRUSTED PUBLISHING (the OIDC form — docs.pypi.org "Trusted publishing"): the repository's own CI authenticating to PyPI WITHOUT a stored token — OpenID Connect: the CI provider mints a short-lived identity token, PyPI verifies it against the REGISTERED publisher, the publish rides a token minted for that one run.
- THE CONFIGURATION (the human hands, at the account's pages): the project's "Publishing" tab (pypi.org/manage/project/{name}/publishing/) — or the account's page (pypi.org/manage/account/publishing/) for the PENDING-PUBLISHER form: registering a publisher for a project name NOT YET uploaded — the CI's first publish CLAIMS the name (the first release's form). The registered parameters (GitHub): the repository OWNER (org/user), the repository NAME, the WORKFLOW FILENAME (the .yml file's name, e.g. release.yml — the docs' "workflow name"), the ENVIRONMENT NAME (optional, recommended — the GitHub Actions environment the job must declare).
- THE MECHANICS at publish: the job runs with permissions id-token: write; the pypa/gh-action-pypi-publish action requests GitHub's OIDC JWT (repo/workflow/ref/environment claims) -> sends it to PyPI's token endpoint -> PyPI verifies the claims AGAINST the registration -> mints a SHORT-LIVED API token (minutes-lived, that one upload) -> the upload completes. NOTHING STORED ANYWHERE: no secret in the repo, no entry at the account's token page. The action can also emit PEP 740 publish attestations (the index serving the publish's own provenance — a form the provenance ruling may weigh). GitLab CI the second supported provider (the docs' provider list).
- THE CUSTODY PRICE: ZERO STORED CREDENTIALS — nothing to leak, nothing to rotate; the trust surface moves to the registration's parameters + the repo/account's own security; a workflow rename breaks the publish until re-registered; the registration rides THE COLLABORATOR'S ACCOUNT (the account ruling's landing).

THE API TOKEN (the alternative):
- THE MINT (the human hands, at the account's page): pypi.org/manage/account/token/ -> "Add API token" -> the scope chosen -> the pypi- prefixed string shown ONCE (copy at the mint moment).
- THE SCOPE'S FORMS: ENTIRE ACCOUNT (all the account's projects) vs PROJECT-SCOPED (one named project — the smaller blast radius: cannot publish other projects, cannot mint tokens).
- THE USE: the upload authenticates username __token__ + the token as the password (twine; the CI's encrypted secrets / .pypirc the carriers).
- THE CUSTODY CLASS: a LONG-LIVED BEARER SECRET — possession = publish power within scope; must be STORED wherever used (the storage surface IS the leak window); revocable at the account's token page; rotation manual.
- THE CUSTODY PRICE COMPARED: the token's price = the stored credential's lifetime surface (leak + rotation + copies); the OIDC's price = the configuration's binding (workflow-name/environment couplings) + the provider federation's trust. Both channels register/mint AGAINST THE COLLABORATOR'S ACCOUNT; both $0 — the design gate rules the choice at the free-tier bar.

(5) THE IMMUTABLE VERSION'S LAW — the first release's number's permanence

- NO REPLACEMENT: an uploaded file is NEVER replaced or overwritten — the same filename is never accepted again (the help's file rules); a version's contents are fixed at the publish moment.
- THE YANK (PEP 592): the withdrawal form that KEEPS the version — the manage page's "Yank release" (an optional reason rides the record); the semantics: THE VERSION STAYS at the index (its files remain at their URLs) while THE RESOLVER BLOCKS it — the simple index marks the files data-yanked (the reason in the URL fragment); pip never PREFERS a yanked file (a normal resolution skips it); a pinned requirement (== the exact version) or a sole-match resolution lands on it WITH a warning (the reason shown); the direct download still works; REVERSIBLE (un-yank restores normal resolution). The broken-release form that never burns the number.
- THE DELETION FORMS: individual files / whole releases deletable at the project's manage page (the maintainer's own act); the PROJECT's deletion only via PyPI admin request.
- THE VERSION NEVER REPUBLISHABLE: the index burns the identity — the filename reserved forever (a deleted file never re-accepted), and the sources' law: a used version number is never re-published (the help's guidance; the ecosystem forbids two byte-sets under one identity — clients may have already cached the old files) — the ONLY fix a NEW number.

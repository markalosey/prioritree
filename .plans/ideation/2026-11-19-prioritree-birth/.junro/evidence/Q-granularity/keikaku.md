## 1. The unboundedness check — where "ANY list and ANY comparison operator" is too broad

The ruled purpose is deliberately unbounded ("generalized… for any list and comparison operator" [STATED, Q-purpose]). Unboundedness is the spec's right; it is a build effort's hazard. Eight axes checked; each gets a FENCE (what the first product effort builds and verifies) and a DEFER (the future ruling that earns the widening). Every fence cuts at a schema seam, so the deferred widening costs zero rework.

F1 — Item-count scale. Too broad where: full pairwise coverage is O(n²) — 10 items → 45 pairs; 100 → 4,950; 1,000 → 499,500; 10,000 → 49,995,000. FENCE [PROPOSED]: the core stays total — every function correct for any n (pure logic is naturally unbounded; no artificial caps) — but the effort's verified workload is n ≤ 100 with full-coverage enumeration. DEFER: sampled/adaptive scheduling, tournament/merge structures, incomplete-coverage ranking confidence — earned by a real list > 100 items at a real gate with the cost measured on that workload.
F2 — Operator class. Too broad where: "any comparison operator" spans total orders, weak orders (ties), partial orders (incomparables), multi-criteria. FENCE [PROPOSED]: one operator instance per list (a stated question bound at session birth, e.g. "which of these two is more important?"); vote domain = the weak-order triple {prefer-a, prefer-b, tie}; the emitted ranking is a total order of tie-groups. DEFER: incomparability/abstention as first-class value, multi-criteria operators, operator composition — earned by a real comparison task whose pairs resist the weak-order triple.
F3 — Vote completeness. Too broad where: "run the pairwise permutations" is ambiguous — n(n−1) ordered presentations or n(n−1)/2 unordered pairs? FENCE [PROPOSED]: full coverage of all unordered pairs, exactly once per comparator per session (n=100 → 4,950 votes); canonical (id-sorted) presentation; the tally stays well-defined at ANY coverage point (pure function of whatever is stored [STATED]) — partial coverage is a legal state, not an error. The "permutations" reading is flagged for ruling (a near question below). DEFER: both-directions order-bias probing, adaptive early-stop, statistical stopping rules — earned by a measured bias datum or an over-expensive full coverage.
F4 — Comparator scope. Too broad where: "both human AND LLM" scales to many humans, many LLM seats, weighted votes, quorum, adjudication — a social-choice problem hiding inside a "store votes, tally" core. FENCE [PROPOSED, on STATED ground]: one vote interface [STATED — the ruled cure]; a comparator is stamped metadata on the vote (id + class ∈ {human, llm}); equal weight at birth (one vote, one tally unit); the core is comparator-agnostic — it never calls a comparator, it only accepts vote records [votes are data in/out — STATED]. The first effort verifies the interface with a scripted/LLM seat; the human vote surface arrives with the web tier (ruled "the human comparator's vote surface" [STATED]). DEFER: multi-comparator populations, disagreement metrics, per-comparator weights, adjudication protocols — earned by a real session with ≥2 comparators on one list; the id/class stamp makes widening additive.
F5 — Session shape. Too broad where: "any list" over time implies open-ended accumulation — items added mid-session, votes invalidated, rankings incrementally recomputed; that is a state-management engine (and eventually the DB the ruling excluded at birth). FENCE [PROPOSED]: the birth session is one list, one operator, one sitting: register → schedule → vote (to exhaustion or stop anywhere) → tally → ranking. The vote store is append-only (corrections are new votes, never edits — the family idiom; the tally as a pure function over the whole multiset makes this sufficient). No session mutation surface at birth. DEFER: open-ended accumulation, mid-session item addition, vote invalidation, incremental re-ranking — earned by a real multi-sitting workload; append-only + pure-tally keeps it reachable without reshaping.
F6 — Item content generality. Too broad where: "any list" could mean strings, documents, images — if the core interprets content, the core inherits every content type's problems. FENCE [PROPOSED]: items are opaque to the core: (id, label/content) rows; the core never interprets content; "any list" enters as opaque rows. Display richness is a wrapper concern. DEFER: typed items, content interpretation, multi-modal items — earned by a real wrapper needing richer display; costs the core nothing.
F7 — Tally determinism (the algorithm fence). Too broad where: "the tally is a pure function of the stored votes" [STATED] rules out statefulness but not the method space: wins-count (Copeland-style), Borda, Bradley-Terry/Elo-style probabilistic scales, Condorcet family — each a different engine with different vote-domain needs. FENCE [PROPOSED]: one tally at birth — wins-count with deterministic tie-break (item id): score = wins − losses; ties group; the tie-break orders groups deterministically so the output is reproducible. The ranking carries per-item wins/losses/ties and coverage counts (partial coverage and future confidence work carry their datum). Purity is the ruled bar [STATED]: same votes in → same ranking out, no environment reads. DEFER: the method family selection (Borda/Condorcet variants), probabilistic scales (BT/Elo), confidence intervals — earned by a real noisy-vote dataset; the method is one module behind the vote multiset, replaceable without touching any other unit.
F8 — The layering fence (the ruled one). Too broad where: all four forms in one effort couples the core to three presentation tiers. FENCE [STATED, Q-setup-arch]: the first product effort = the library only; CLI wraps, FastAPI serves, web fronts — each a named future increment; no DB (persistence is a service-tier design ruling); CI deferred; the core keeps zero runtime dependencies (pyproject dependencies = [] measured — keeping it is [PROPOSED] as a fence).

Tight couplings named and cured: (a) core↔comparator — cured by the one vote interface [STATED]; (b) core↔presentation — cured by opaque items + wrappers own display; (c) tally↔scheduling — cured by the tally reading only stored votes, never asking how pairs were chosen [STATED purity]; (d) store↔tally — coupled only through the vote schema, pinned at the store's brief (the exact seam that prevents FR-MEM-0001's class: shapes inherited from a record made outside their owning unit's census).

## 2. The atomic decomposition — six units, the route's own grammar

Every unit carries the route's proven per-unit pipeline wholesale [STATED grammar]: discover/<unit> (tansa, ungated) → understand/<unit> (rikai, ungated) → synthesize/<unit> (togo, gated increment @ G-<UNIT>-BRIEF, collaborator-ruling: brief landed + approved) → build/<unit> (jikko @ G-<UNIT>, deterministic-check; the exact-task law — the brief is the spec) → validate/<unit> (kensho, independent re-run). Landing rhythm: one-commit-per-increment; revert: one-increment. Unit names follow the naming law (each act-statement begins with its unit's name).

U1 · registry — the item registry + the core schemas. Act: Register the list's items as opaque rows (id, label) and bind the session's single comparison operator (a stated question), owning the item/operator/list schemas every other unit cites. Verification hook: G-REGISTRY (deterministic-check) — schema round-trips green, duplicate-id refusal, empty-list edge; the zero-and-zero floor (ruff + pyright) on kensho's independent run. Must NOT know (Parnas): scheduling strategy, vote semantics, ranking, who votes, how items display — the root vocabulary; nothing downstream revises it.
U2 · scheduler — the pair scheduler. Act: Schedule the full pairwise coverage queue — every unordered pair of registered items exactly once (n(n−1)/2, canonically id-sorted), in a deterministic enumeration order, given only the item-id set. Verification hook: G-SCHEDULER — property tests: exact pair count (10 → 45, 100 → 4,950), zero duplicates, order-stable across runs, empty/1-item edges. Must NOT know: vote values, comparators, the operator's meaning, where votes go — it mints the canonical pair form every vote cites.
U3 · votes — the vote store (append-only). Act: Votes append immutably to the session's vote ledger — a comparator-stamped judgment (id, class, value ∈ {prefer-a, prefer-b, tie}) on a canonical pair, validated against the registry (unknown ids/pairs refused), read back as data in/out. Verification hook: G-VOTES — append-only invariant verified at the module surface (no mutation verb exists), re-vote behavior matches the brief's ruled semantics, unknown-item/pair refusal, ledger read-back byte-true. Must NOT know: ranking, enumeration strategy, comparator implementation — it pins the vote schema U4 consumes, the sole contract between store and tally.
U4 · tally — the tally engine (pure function). Act: Tally the stored votes into a ranked whole — the pure function whose input is the vote multiset and whose output is the ordered tie-grouped ranking with per-item wins/losses/ties and coverage counts, deterministic tie-break included. Verification hook: G-TALLY — purity property (same votes → same ranking; no environment reads), known-answer fixtures (hand-computed), well-defined ranking at every coverage prefix, tie-break stability; verifiable on fixtures alone. Must NOT know: scheduling, comparator identity, storage medium — the product's ruled heart [STATED: "the tally is a pure function of the stored votes"].
U5 · session — the ranking emission / read surface (the public face). Act: Session the chain into the library's public face — register → schedule → vote → tally composable at any coverage point, emitting the stable ranking serialization (the read surface the wrappers cite). Verification hook: G-SESSION — end-to-end fixture (a scripted vote sequence → the exact expected ranking), prefix-tally property, the public API frozen as the wrapper contract. Must NOT know: CLI/service/web concerns, comparator elicitation UX — the information-hiding boundary that lets all three wrappers arrive with zero core rework.
U6 · acceptance — the acceptance harness (what proves "superior order"). Act: Accept the product at the ruled bar — the seed-deterministic simulation harness: items with a latent total order, votes sampled from noisy comparators at stated noise rates, asserting the tallied ranking recovers the latent order (Kendall-tau ≥ the ruled floor). Verification hook: G-ACCEPTANCE — seeds fixed so the simulation is byte-reproducible on kensho's independent run; the threshold itself is a collaborator ruling banked at the brief (the assessment axis — what bar counts as "superior" is a judgment; the machinery that measures it is deterministic). Must NOT know: any private surface — only the U5 public API (it is the first consumer, standing in for the wrappers).

Coupling discipline: the dependency graph is U1 → {U2, U3} → U4 → U5 → U6, and every edge is a schema citation pinned at the upstream unit's brief gate — no unit imports another's internals, no shape is decided outside its owning unit's pipeline (FR-MEM-0001's lesson, folded in as a design rule).

## 3. The minimal first increment

U1 registry — first, alone. Reasons: (1) the ruled organ order starts with items [STATED — Q-setup-arch lists "items, comparison operator, pair scheduling, votes, tally" — the layering's own sequence is the dependency order]; (2) its shapes are terminal — item ids, labels, and the operator question are revised by nothing downstream — zero rework by construction; (3) it unblocks both parallel legs at once: U2 (scheduler) and U3 (votes) are siblings that cite only U1's vocabulary; both pipelines open the moment G-REGISTRY-BRIEF is green; (4) the alternative loses: U4-first would pin the vote schema and its item-id references inside the tally's brief — shapes owned by units whose discovery legs haven't run; that is exactly FR-MEM-0001's data-gap class.

The remaining order and its reasons: U2 scheduler (2nd — mints the canonical pair form every vote cites) → U3 votes (3rd — pins the vote schema; U4's discovery may open at its brief-green, the route's ungated-packet pattern) → U4 tally (4th — the pure heart over the pinned schema, fixture-verified) → U5 session (5th — the public face; its green gate is what the CLI/service/web efforts wait on) → U6 acceptance (6th — the proof over the public face, at the ruled bar).

Near-term questions that ride the briefs (the route's own pattern — questions open in the store, resolved at the unit's legs, the gate holds the proof): the "permutations" reading (U2's brief): unordered-pairs-once [PROPOSED default] vs both-directions bias probing; re-vote semantics (U3's brief): append-and-accumulate [PROPOSED default] vs latest-wins per comparator per pair; the tally method + tie-break (U4's brief): wins-count with id tie-break [PROPOSED default] vs another member of the method family; the superior-order bar (the effort's open question, landed at U6's brief): what noise rates and what Kendall-tau floor prove "superior" — the one genuine assessment ruling in the chain.

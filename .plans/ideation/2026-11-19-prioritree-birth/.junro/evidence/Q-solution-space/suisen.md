## §0 — The answer in one line

One stochastic act (the vote), confined behind one schema-validated write; everything else — scheduling, ingestion, tally, emission, lookups — deterministic; the interface is five ops over two append-only stores, with the tally algorithm and the scheduling policy hidden behind module seams so both are revisable without touching a single record.

## §1 — The stochastic/deterministic split

| Act | Class | Why | Input variety it must absorb (Ashby) | What it refuses (the gate) |
|---|---|---|---|---|
| (a) The VOTE (pairwise elicitation, human or LLM) | STOCHASTIC — the only one | The vote's content is the very fact the system lacks (see below) | Any well-formed judgment: any pair, any verdict, any count, from either comparator class, including repeated and reversed samples | Nothing on content — the gate asks "well-formed?", never "correct?" |
| (b) Pair selection (scheduling) | Deterministic (function of vote state + explicit seed) | Scheduling is information-gain selection; the state already holds everything judgment could add — an LLM picking pairs adds no information and makes the pair stream unauditable | The n·(n−1)/2 permutation space; coverage gaps; the "no pair remains" terminal | <2 items; the exhausted state (the DONE signal, distinct from error) |
| (c) Vote ingestion | Deterministic gates | Schema validation, idempotency, dedup, ground-truth lookups — all mechanical | The malformedness space: wrong types, unknown ids, bad enums, duplicate sends, revotes, corrections | Every malformed payload, with expected/found/next-action naming the store's truth |
| (d) Tally | Deterministic (ruled pure — junro.json:429); recommend win-rate/Copeland | See the tally ruling below | Multi-vote pairs, ties, cycles, supersessions, sparse coverage | Nothing — the tally never refuses content; the emission gate (e) refuses on coverage |
| (e) Ranking emission | Deterministic, idempotent actuator | A projection of (d); same vote state → byte-identical output; zero write target | Ties, thin-evidence items, cycles | The safe halt: under-coverage — expected/found/next-action naming the isolated items and the closing pairs; never a partial ranking dressed as whole |
| (f) Ground-truth lookups (item registry = the run manifest) | Deterministic | Pure reads over the frozen manifest; the find-before-create precedent | All id claims from any caller | Unknown ids — the refusal names the legal set |

(a) Why judgment cannot be deterministic. A deterministic function's output is derivable from its inputs. The vote's content — "A exceeds B under operator O" — is precisely the fact not derivable from anything the system holds: the items' stored bytes do not encode their relative order, and if they did there would be no product (you would sort by the bytes — Q-purpose's whole premise is that discernment is what comparators do and sizing is what they cannot). The judgment enters the system from outside — human semantics or model policy. Technically: an LLM's output is a sample from a policy distribution (same prompt, different draws); practically: a human's judgment is noisy (fatigue, context, order effects — the same pair twice may get different verdicts; Thurstone's 1927 ground). Therefore votes are noisy measurements of a latent order, treated as data — never as ground truth. The deterministic plane's job is measurement hygiene (schema, dedup, provenance) and aggregation (the tally), never measurement itself. Both comparator classes enter through the one write (junro.json:429): comparator_class is a data field riding the vote, never a second interface.

(d) The tally ruling — win-rate (Copeland-style), for increment 1. Score_i = (wins_i + 0.5·ties_i) / comparisons_i. Point accumulation — refused as default: it conflates exposure with strength; the ruled architecture names pair scheduling as a core noun (junro.json:442), so schedules will be uneven — an item compared more often accumulates more points regardless of quality; raw points are biased by construction under this product's own architecture. Elo — refused by the ruling itself: an online sequential update — the rating depends on the arrival order of votes; "the tally is a pure function of the stored votes" (junro.json:429) reads on the vote set; order-independence is the purity; sequential update is also stateful scoring, contradicting "stateless scoring/ranking core" (junro.json:442). Bradley-Terry — deferred, earned later: statistically the strongest (weights by opponent strength), but it carries iterative numerics with convergence edge cases (undefeated items → unbounded MLE; disconnected graphs → unidentified parameters; regularization priors = a second design decision riding the first), and its superiority only materializes on dense connected vote graphs — not the birth regime (sparse votes, small n, k≈1 per pair). Win-rate — recommended: order-independent batch (satisfies the purity ruling verbatim); closed-form, zero iteration, zero tuning; unbiased under uneven schedules (each item scored by its observed win fraction — the scheduler's shape buys no points); degrades gracefully on sparse data; honest about its own limits (a 1.0 score on one comparison is exposed as thin evidence by the per-item counts in the emission).

The Parnas fold (the task's explicit demand): the vote record carries no score field; ingestion computes nothing; the tally lives in one module behind op 5. The pure-function ruling permits any tally — so the vote interface must not leak the choice, and here it cannot: there is no field to leak through. Swapping Copeland → BT later touches exactly one module; zero vote records migrate; zero comparators notice. The emission carries an algorithm version stamp (auditability without coupling).

## §2 — The narrowest tool interface (five ops)

1. register_run(items, operator, quorum=k) → RUN-{####}. Act: register a run — the immutable (items, operator) ground. Inputs: ≥2 items (stable id + payload each), one operator declaration (id + allowed verdict set — binary at birth, tie per declaration), quorum policy (default k=1) — policy is data, not code. Refusals: <2 items; duplicate ids within the payload; schema violations — all expected/found/next-action. Side effects: exactly one — the run manifest append, frozen thereafter. Hides/forecloses: there is no mid-run item mutation op — add/remove/rename are unrepresentable, so item drift is foreclosed by construction, not policed; folding the operator in is the same move: standalone items would make cross-operator vote pollution representable; the run makes it unrepresentable. An op set that cannot express a hazard is narrower than one that can but refuses.
2. next_pair(run_id, seed?) → (item_a, item_b, pair_vote_count). Act: next pair — the scheduler read. Pure; default seed derived from run_id → replays byte-match. Refusals: unknown run; the exhausted state (no under-quorum pair remains) → the DONE signal, named, distinct from error. Side effects: zero. Hides/forecloses: the scheduling policy (increment 1 ships complete round-robin over the permutation set — the ruled mechanism verbatim, README.md:3; adaptive selection for large n is a later earned upgrade behind this seam). The pair returns no state, no scores — elicitation purity: the comparator must not see the current ranking (anchoring/order-effect contamination is the psychometric hazard; the bare pair is the only valid elicitation context). Forecloses comparator-chosen pairs (adversarial pair-gaming) and ambient nondeterminism.
3. cast_vote(run_id, pair, winner, comparator_id, comparator_class, notes?) → VOTE-{####} + post-append ledger count. Act: cast a vote — the only stochastic-side entry point, and the only op that mutates the vote ledger. The schema gate is the stochastic/deterministic boundary. Gates: strict schema; winner ∈ the pair's declared verdict set; both item ids ground-truth-checked against the run manifest at write time (FR-MEM-0001's discipline); comparator_class ∈ {human, llm}; provenance stamp on every line (actor, timestamp, session) — the family law. Idempotency: canonical-content dedup — a byte-identical re-send is a loud idempotent ack naming the original handle (never silent — FR-MEM-0143's lesson); a changed verdict from the same (comparator, pair) is a new record (a revote is a new sample — changed minds are information). Clerical corrections ride supersedes: VOTE-{####}. Refusals: unknown run/item ids; winner not in pair; malformed payload — naming the legal set. Never refuses on content plausibility (the system has no opinion about votes — noise is data). Ingestion is independent of the scheduler: a vote is valid on any registered pair (the scheduler suggests; it does not confer permission — keeping them decoupled preserves the Parnas seam and serves both comparator classes). Side effects: exactly one — the append to the vote ledger. Hides/forecloses: any notion of score (nothing to leak through); the return carries the post-append count — a built-in self-verification leg. Forecloses vote edit/delete (unrepresentable — append-only), score smuggling, vote-time ranking access. Abstention needs no record: a comparator who cannot judge simply does not cast; the pair stays under-quorum.
4. read_vote_state(run_id) → manifest, per-pair counts, per-item comparison counts, coverage/connectivity verdict, the full vote log. Act: read the vote state — the census read-back instrument. Pure. Refuses: unknown run only. Never refuses on coverage — the audit surface must read back even a broken state, especially a broken state; that is its job (the op that catches FR-MEM-0143-class silent loss and FR-MEM-0001-class gaps; every gate's evidence leg rides it). Side effects: zero.
5. tally_rank(run_id) → ranked list (ties as shared ranks, stable id-order presentation), per-item comparison counts, coverage verdict, algorithm version stamp. Act: tally and rank — the pure projection. Idempotent: same vote state → byte-identical emission. Write target: nothing — the actuator emits; the caller lands the output. Refusal — the safe halt: coverage gate unmet — (i) any zero-coverage item, (ii) the comparison graph disconnected, or (iii) per-pair quorum unmet → expected/found/next-action naming the isolated items/components and the exact pairs that close the gap. Never a partial ranking dressed as whole; never an empty list (a named refusal is data; silence is not). Hides/forecloses: the tally algorithm and the supersession/dedup weighting policy (both live inside this module). Forecloses under-coverage confident lies and nondeterministic tie handling — a tie is reported as a tie.

Why five, not fewer (the merge-refusals): ops 4+5 must not merge (the audit read must never refuse on coverage; the emission must always refuse on it — one op cannot do both honestly); ops 2+4 must not merge (the comparator surface must not see state; the auditor must — merging leaks the ranking to the judge); op 1 must not shed the operator (cross-operator pollution becomes representable). Total mutation surface: two append-only stores (run manifests, vote ledger), zero edit/delete verbs, corrections as new entries referencing the old. Unintended-side-effect classes foreclosed by the narrow interface: silent record loss (single choke-point write + loud idempotency + built-in read-back); unverified payload acceptance (ground-truth lookups at write time); history rewriting (no verb exists); score/tally coupling (no score field); item drift (no mutation op); comparator anchoring (state-blind next_pair); cross-operator pollution (votes live under a frozen run); partial-ranking lies (the coverage gate); ambient nondeterminism (explicit seeds, order-independent tally, stable tiebreaks — replays byte-match).

## §3 — The hazard fold-in (the repo's learned frictions as design requirements)

FR-MEM-0143 — parallel-write races silently lose records (junro.json:474, the re-fire note: both OK lines returned, one record clobbered; "any parallel route-op pair is unsafe"). The discipline: (1) One mutating op per store (cast_vote for votes, register_run for manifests) — the write surface is a single choke point; the family's own record home already carries the pattern (.junro/.junro.json.lock, .junro/.packets.jsonl.lock) — adopt the lock-file discipline at the vote ledger: exclusive append held across count → append → verify. (2) A concurrent write refuses loudly (expected: free ledger; found: lock held; next: retry sequentially) — a refused write is data; a lost write is corruption. (3) Honest boundary at birth: single-process contract documented in the module contract; the service tier later owns serialization (no DB — junro.json:442). (4) OK lines are not evidence; the store is: cast_vote returns handle + post-append count (self-verification built into the return); the deep read-back rides op 4. The orchestration law above the core: sequential writes over one run's ledger, always.

FR-MEM-0001 — unverified payload data-gaps (.plans/state/friction-ledger.jsonl:1: a fenced payload carried a wrong root, inherited from an upstream record's payload; caught only because the builder validated the bytes against the route-ruled ground truth, not the payload's provenance). The discipline: validate against the store's own truth at write time, never against the payload's provenance: (1) register_run checks the payload against itself (duplicate ids) — even trusted-source payloads are untrusted bytes; (2) cast_vote checks every id claim against the run manifest, every verdict against the declared set — the refusal names the legal set and the store's truth, so the gap is mapped, not merely blocked; (3) the write returns what landed, not what was sent — send-vs-stored is diffable by the caller.

The append-only law — the concrete form: no edit op, no delete op; corrections are new entries referencing the old. Two correction forms, both append-only: changed mind = a new sample (both count — information); clerical error = supersedes: VOTE-{####} (the old stands in the log, excluded by the tally's weighting — and that weighting policy lives inside the tally module, swappable without record migration).

## §4 — The Ashby check (where input entropy could exceed variety, and what absorbs it)

| Entropy source | Absorber |
|---|---|
| Noisy votes (same comparator, contradictory samples) | The schema's variety must match the judgment space: any well-formed vote, any count — refusing the second sample from the same comparator would discard the psychometric remedy (repetition averages noise — Thurstone). Multi-vote-per-pair is representable from day one; the tally's fractional scores do the averaging. |
| Cycles (A>B, B>C, C>A) | Not errors — a mathematical certainty of aggregated judgment (Condorcet; Arrow: no procedure is globally consistent). The tally's fractional arithmetic dissolves cycles into win fractions; ties get shared ranks; the cycle is named in the coverage data. The system never "resolves" a cycle by judgment — that would inject stochasticity into the deterministic plane. |
| Adversarial voters | Honest boundary: the birth tally is not adversarially robust (trusted-comparator/benign-group regime assumed — stated, not hidden). The hedge is the record: comparator identity stamped on every vote makes future weighting retro-fittable with zero record migration. Pair-gaming is foreclosed structurally: the comparator never chooses pairs. |
| Item drift | Unrepresentability — the immutable run; a changed list is a new run. |
| Malformed transport input | Strict schema + expected/found/next-action; the refusal set is the variety. |
| The confident lie (partial information that looks complete) | The coverage gate — the safe-halt refusal names the disconnected components and the closing pairs. The worst failure class by detectability (hidden), and the gate is its only absorber. |
| Scale (n² pair space) | Increment 1 ships complete round-robin (the ruled mechanism verbatim; n small at birth); the hidden scheduler seam is where adaptive selection is earned later — the interface absorbs growth without changing shape. |
| Tie entropy | Shared ranks + stable id-order presentation — a tie reported as a tie; presentation deterministic for replay. |

## §5 — The single most important recommendation

cast_vote's write discipline — the single mutating op, with schema validation, ground-truth lookups at write time, loud idempotent dedup, minted handles, provenance stamps, and the built-in read-back (handle + post-append count). Reasoning, by irreversibility: every other choice in this set — tally algorithm, scheduler policy, tie rules, quorum policy — is reversible by construction: hidden behind a module seam, revisable without touching a single record (Parnas bought that cheapness deliberately). The stored judgments are not reversible: votes are the product's only irreplaceable asset — re-eliciting a human's judgment is not recovery, it is a different sample — and a ledger that silently loses records (FR-MEM-0143) or silently accepts unverified payloads (FR-MEM-0001) poisons every tally ever run over it, undetectably from the output side. The repo's own two recorded frictions are both instances of exactly this class, and both were caught by read-back against ground truth, never by the write's OK line. Therefore the write path is where the design must spend its strictness; everything else can be revised behind a seam.

# SUISEN — design/flows — part b (a: design-flows-a.md; c: design-flows-c.md) — FLOWS 2-3

**FLOW 2 — THE SITTING**
- Screen `sitting` (`/runs/{id}`): the stated question as the prompt; the BARE pair — two item cards, labels only, the canonical id-sorted order as served (R7); verdict buttons rendered from the **declared** set; the comparator identity (id entry at sitting start, class `human` stamped — Q-solution-space R5). NOTHING else: no scores, no counts, no progress, no ranking. The envelope's `count` fields render nowhere on this screen.
- Steps: enter comparator id → the pair renders → a verdict button → the ack → the next pair → … → the DONE body → screen `sitting-done`: "every pair judged", the DONE body's expected/found rendered (no elicitation remains — showing coverage now is safe), the link to the ranked whole.
- HTMX: the pair region `hx-get=".../next"` (**QUERY**); each verdict button `hx-post=".../votes"` (pair, winner, comparator_id, comparator_class) targeting an ack strip (**COMMAND**); the ack fragment renders the loud idempotent ack — vote_id + acknowledged, count unrendered (a byte-identical re-send acks naming the original handle, R9) — and embeds `hx-trigger="load" hx-get=".../next"` into the pair region (**QUERY**). A 422 vote refusal leaves the pair region intact — the same pair retryable, the sitting unharmed. No seed control surfaces — the default (run_id-derived) rides; determinism is not a comparator concern.
- **RECOMMEND: the two-step chain (POST ack → GET next), never the merged one-round-trip. Why:** R2's segregation made structural — the pair presentation NEVER rides a command's response, so the no-anchoring boundary is architectural, not incidental; the shapes mirror the wire's existing ack exactly; and a refused vote cannot clobber the elicited pair.
- **RECOMMEND: hide every count from the comparator. Why:** "the bare pair is the only valid elicitation context" (Q-solution-space suisen.md, op-2's forecloses) — pair-count is ambient information the judgment doesn't need; hiding costs nothing and forecloses the surface.

**FLOW 3 — THE PROGRESS view (the operator's audit surface)**
- Screen `progress` (a separate route, NEVER embedded in `sitting`): the census read rendered verbatim — total votes + per-item involvement (the wire's `{"total","items"}`; `per_pair_counts` elided at the seam — the design does not resurrect what the seam dropped).
- The comparator MAY see mid-sitting: the pair, the question, the buttons, their own identity and ack. NOTHING more. Only the OPERATOR may see: total votes, per-item counts, the audit fold. Mid-run ranking cannot leak even by navigation — the 409 SAFE HALT refuses until coverage (the honest boundary does the hiding for us).
- HTMX: `hx-get=".../state"` with `hx-trigger="every 5s"` (or a manual refresh). **LANE: QUERY** — the pure read that never refuses on coverage.
- **RECOMMEND: progress is a separate screen the operator navigates to deliberately, never a panel beside the pair. Why:** ops 2+4 must not merge (Q-solution-space: "the comparator surface must not see state; the auditor must — merging leaks the ranking to the judge"); surface separation keeps the leak a deliberate act, never ambient. When one human holds both seats the discipline is theirs — the design refuses to make contamination frictionless.
